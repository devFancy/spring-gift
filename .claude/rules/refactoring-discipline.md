# refactoring-discipline

과제5 의 프로그래밍 요구 사항 10개 원칙을 spring-gift 작업 규칙 문장으로 재서술한 룰 + 본 과제 특화 1개 항목. 원문 인용은 하지 않는다. 본 과제는 리팩터링 전용이며, 4번 단일 목적 원칙도 그 맥락에서 해석한다.

## 1. 코드 품질 자기 책임

AI 가 변경한 코드도 사람이 책임진다. 변경 후 코드 복잡도, 가독성, 테스트, 커버리지를 직접 확인한다. "행동만 맞으면 된다" 로 끝내지 않는다.

## 2. 계획 파일 기준

작업은 "다음 한 가지" 가 명확해야 시작한다. README 의 기능 목록 또는 plan-file 의 체크리스트에 항목이 잡혀 있어야 코드 수정을 시작한다. 잡혀 있지 않으면 작업 전에 항목을 먼저 추가한다.

## 3. TDD 루프

가능하면 Red -> Green -> Refactor 순서로 진행한다. 최소 기준은 "변경 후 전체 테스트 통과" 다. 통과 없이 다음 변경으로 넘어가지 않는다.

## 4. 단일 목적 커밋

한 커밋은 하나의 목적만 담는다. `git diff` 만 보고 의도를 30초 이내에 설명할 수 있어야 한다. 본 과제는 리팩터링 전용이지만, 그 안에서도 도메인이 다르거나 의도가 다른 변경(테스트 추가, 문서 변경, 빌드 설정 등)이 한 커밋에 섞이지 않게 분리한다. (커밋 메시지 type 규칙은 `.claude/rules/commit-discipline.md` 참고.)

## 5. 한 번에 한 조각

변경 범위는 "다음 변경 1개" 로 제한한다. AI 에게도 현재 변경 범위를 명확히 좁혀 지시한다. 한 번에 여러 도메인, 여러 계층을 동시에 건드리지 않는다.

## 6. 진행 속도 통제

반복이나 복잡도가 갑자기 늘거나, 요청하지 않은 작동이 추가되면 작업을 중단하고 원인을 확인한다. 테스트를 회피하거나 비활성화하는 변경은 허용하지 않는다 (예: `@Disabled`, `@Ignore`, assertion 제거).

## 7. 커밋 논리 단위

하나의 커밋은 하나의 목적만 가진다. 동일 커밋에 여러 도메인의 잡일이 섞이지 않도록 stage 단계에서 파일 단위로 분리한다.

## 8. AI 산출물 검증

AI 가 만든 코드는 초안이다. 설계와 검증 책임은 사람에게 있다. 중간 결과물을 자주 확인하고, 의도하지 않은 변경은 즉시 제거한다.

## 9. 리팩터링은 작동 보존을 증거로 보인다

리팩터링 후에는 변경 전과 동일한 작동을 유지함을 증거로 보여야 한다. 기존 테스트 전체 통과가 1차 증거다. 기존 테스트가 없는 영역이면 변경 전에 작동 보존 테스트를 먼저 추가한다 (별도 test: 커밋으로 분리한다). 통과한 테스트가 실제 작동을 충분히 캡처하는지 한 번 더 확인한다. 검증 절차는 `.claude/rules/testing-discipline.md` 참고.

## 10. ADR 작성 조건 (기술 선택 근거 포함)

다음 중 하나라도 해당하면 `docs/adr/` 에 ADR 을 작성한다 (디렉토리는 필요해질 때 만든다).
- 선택지가 2개 이상이고 트레이드오프가 있다 (기술/라이브러리/외부 의존 도입 포함).
- 반복적으로 따라야 할 규칙이나 경계를 새로 정의한다.
- 테스트 전략이나 검증 방식이 결정의 핵심이었다.

위 조건에 해당하지 않으면 ADR 을 만들지 않는다. 단, 기술 선택은 "단순히 사용한다" 로 끝내지 않고 근거를 README 또는 ADR 에 한 단락으로 남긴다.

## 11. 과제 자료 원문 인용 금지

과제 PDF, 비공개 정리본, 외부 자료의 원문 문장을 공개 파일(README, 커밋 메시지, ADR, 룰 파일 등)에 그대로 옮겨 적지 않는다. 자기 언어로 재서술한 룰 문장으로 작성한다.

- 비공개 자료(`docs/private/*`)의 내용은 공개 파일에 원문 인용 금지.
- 외부 자료(블로그, 책)에서 가져온 문장은 자기 표현으로 재서술 후 출처만 표기.
- README 에 과제 요구사항을 정리할 때도 자기 언어로 작성한다. 단순 복사 붙여넣기는 학습 가치도 없고 과제 의무 위반이다.

## 적용 시점

- 작업 시작 전: 2번, 5번을 점검한다.
- 변경 중: 1번, 6번, 8번을 점검한다.
- 커밋 직전: 4번, 7번, 9번을 점검한다.
- 변경 종료 후: 10번 (ADR 필요 여부), 11번 (원문 인용 점검) 을 점검한다.

`/refactor-step` skill 흐름이 위 시점을 단계로 가지고 있다.
