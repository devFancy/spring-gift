# commit-discipline

커밋 절대 준수 4개 항목과 spring-gift 커밋 컨벤션을 명문화한 단일 출처 룰. 본 룰은 다른 모든 룰과 충돌 시 항상 이긴다. CLAUDE.md 는 본 파일의 우선순위만 라우팅으로 명시하고 절대 준수 본문은 옮겨 적지 않는다 (drift 방지).

## 절대 준수

### 1) 자율 실행 금지

Claude 는 `git commit`, `git push`, `gh pr create` 를 자율적으로 실행하지 않는다.
- 사용자가 "커밋해 줘", "PR 올려 줘" 같은 명시적 신호를 보낼 때만 실행한다.
- "기능 완료", "테스트 통과" 같은 상태 보고만으로는 커밋하지 않는다.
- 변경 작업이 끝나면 `git status` + `git diff` 결과를 보여주고 멈춘다.
- 사용자 승인 후에도 커밋 메시지 초안을 먼저 보여주고 실행 직전 한 번 더 확인한다.

### 2) AI 출처 표기 금지

커밋 메시지에 다음을 절대 추가하지 않는다.
- `Co-Authored-By: Claude ...` 형식의 모든 Co-Authored-By 라인.
- `Generated with Claude Code` 같은 AI 출처 표기.
- author 정보를 변경하지 않는다.

### 3) 단일 목적 커밋

한 커밋은 단일 목적만 가진다. 본 과제는 리팩터링 전용이므로 새 작동 도입은 발생하지 않지만, 그 안에서도 다른 도메인이거나 다른 의도(테스트 추가, 문서 변경, 빌드 설정 변경 등)인 변경이 한 커밋에 섞이지 않게 분리한다. `git diff` 만 보고 의도를 30초 이내에 설명할 수 있어야 한다.

### 4) 위험 명령 차단

위험 명령은 사용자 명시 요청 없이 실행하지 않는다.
- `git push --force` 또는 `-f`, `git reset --hard`, `git rebase` (대화형 포함).
- `git checkout` 으로 변경 폐기, 브랜치/태그 삭제.

## 커밋 메시지 형식

```
<type>(<scope>): <한국어 제목>

<선택> 한국어 본문, 정말 중요한 결정/이유 1, 2줄.
```

### type (5개만 사용)

본 과제는 리팩터링 전용이라 새 작동을 도입하는 `feat` 는 사용하지 않는다.

| type | 용도 |
| --- | --- |
| refactor | 리팩터링 (구조 변경, 작동 보존). 포맷팅/스타일도 흡수 |
| fix | 버그 수정 |
| test | 테스트만 추가/수정 |
| docs | README, 주석, 문서 변경 |
| chore | 빌드, 의존성, 도구 설정 |

다른 type(style, perf, build, ci 등)은 chore 또는 refactor 로 흡수한다. 새 type 을 추가하지 않는다.

### scope

도메인 단위 사용: auth, member, product, option, category, order, wish. 인프라 작업이면 build, config 도 허용한다. 여러 도메인에 걸치면 가장 핵심 도메인으로 지정한다. scope 가 정말 모호하면 생략 가능하지만 권장하지 않는다.

### 제목

한국어, 50자 이내. 명령형/평서형 일관성 유지. 마침표 없음.

유스케이스 기반의 도메인 유비쿼터스 언어(상품, 주문, 카카오 로그인, 위시리스트, 옵션, 회원 등)로 작성해서 UX 관점에서 누구나 이해할 수 있게 한다. 기술 어휘(Controller, Repository, Service, JPA, ArgumentResolver, Repository 등)는 제목에 노출하지 않는다. PM, 신입 동료, 비개발자 협업자가 봐도 변경의 의미를 이해할 수 있어야 한다.

리팩터링 작업의 본질이 기술적이라도, "어떤 사용자 경험/도메인 흐름이 정리되는가" 의 관점으로 표현한다.

### 본문

정말 중요한 결정/이유만 1, 2줄. 불필요하면 생략. 길어지면 안 된다. 변경 요약은 type/scope/제목으로 이미 드러나므로 본문에서 반복하지 않는다.

## 예시

좋은 예 (도메인 유비쿼터스 언어):
- `refactor(product): 상품 조회 책임 정리`
- `refactor(auth): 카카오 로그인 흐름 정리`
- `refactor(wish): 위시리스트 담기 흐름 정리`
- `test(order): 주문 저장 시나리오 통합 테스트 추가`
- `docs: README 에 카카오 로그인 흐름과 AI 활용 기록 추가`

나쁜 예:
- `refactor(auth): KakaoAuthController 메서드 분리` (기술 어휘만, 비개발자가 의미 모름)
- `refactor(product): ProductService 추출` (기술 어휘만)
- `refactor: 여러 가지 정리` (목적 불명확, scope 누락)
- `chore: 리팩토링 + 카카오 토큰 갱신` (단일 목적 위반, type 부정확)
- `refactor(all): 전체 패키지 재배치` (한 조각 원칙 위반)
- `fix: bug` (영문, 정보 없음)

## 커밋 직전 체크리스트

1. 이 변경의 단일 목적이 분명한가. 한 가지로 좁혀졌는가.
2. `git diff` 만 보고 30초 안에 의도 설명 가능한가.
3. 제목에 기술 어휘가 노출되지 않았는가. 도메인 유비쿼터스 언어로 적혔는가.
4. 메시지에 Co-Authored-By, AI 출처 표기가 없는가.
5. 위험 명령이 포함되어 있지 않은가.
6. 사용자에게 메시지 초안과 diff 를 보여주고 명시적 승인을 받았는가.

6번이 핵심이다. `/refactor-step` skill 의 마지막 단계가 이 체크리스트를 자동 적용한다.
