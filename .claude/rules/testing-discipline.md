# testing-discipline

spring-gift 테스트 작성과 실행에 대한 룰. TDD 루프, 두 가지 테스트 유형, 리팩터링 작동 보존 증거 기준을 다룬다. 테스트 도구는 JUnit 5 + AssertJ 를 사용한다. 파레토 원칙(20:80)을 spring-gift 맥락에 적용한다.

## TDD 루프

- 가능하면 Red -> Green -> Refactor 순서로 진행한다.
- 최소 기준은 "변경 후 전체 테스트 통과" 다. 통과 없이 다음 변경으로 넘어가지 않는다.
- 리팩터링은 기존 테스트가 그대로 통과해야 한다. 통과시키려고 테스트를 약화시키지 않는다.

## 두 가지 테스트 유형

### 도메인 정책 단위 테스트

- 대상: `domain/policy/*Policy`, `domain/` 의 순수 도메인 모델.
- 외부 의존 없이 POJO 단위로 검증한다. Spring Context 없이 빠르게 실행되어야 한다.
- 테스트 패키지: 대상과 동일하게 미러링 (예: `domain/policy/ProductPolicyTest`).
- 우선 대상: 범위 검증, 단위 계산, 도메인 규칙.

### 사용자 시나리오 통합 테스트

도메인 작업 시 두 종류의 통합 테스트를 함께 작성한다. 둘 중 하나만 만들지 않는다.

- `{Domain}ControllerTest` (`api/{domain}/`): HTTP 진입점에서 외부 계약(URL, 인증, status code, 권한)을 검증한다.
- `{Domain}ServiceTest` (`application/{domain}/`): 인증을 우회한 비즈니스 흐름 자체를 검증한다. 도메인 정책 분기, 운영자 흐름, idempotent 보장 등 ControllerTest 가 닿지 않는 시나리오 중심.

공통 사항:
- `IntegrationTestSupport` (또는 spring-gift 에 신설할 동등 클래스) 를 베이스로 한다. `@SpringBootTest` + `DatabaseCleaner` + 테스트 전 truncate 패턴.
- 테스트 패키지는 대상과 동일하게 미러링한다.
- 클래스 `@DisplayName` 은 도메인 비즈니스 어휘로 작성하고, `@Nested` 로 시나리오 그룹을 만든다.
- 파레토 원칙을 적용한다. 모든 메서드를 다 검증하지 않고 비즈니스적으로 가치가 큰 시나리오만.

## 파레토 원칙 (20:80)

- 테스트 코드 20% 로 비즈니스 신뢰성 80% 를 확보하는 것을 목표로 한다.
- "이 테스트가 실제로 가치 있는가" 를 먼저 묻는다. 가치 없는 테스트는 작성하지 않는다.
- 단위 테스트를 우선하고, 통합 테스트는 핵심 흐름에만 둔다.

## 작성 기준

- 빠른 피드백 우선: 단위 테스트가 통합 테스트보다 압도적으로 빨라야 한다.
- 독립성: 테스트 간 상태 공유 금지. 각 테스트는 독립 실행 가능해야 한다.
- 엣지 케이스 집중: 경계값, 예외 흐름, 폴백 시나리오 위주.
- 문서 역할: 테스트만 읽어도 비즈니스 요구사항을 파악할 수 있어야 한다.

## 네이밍과 구조

- BDD 패턴 사용: `// given`, `// when`, `// then` 주석으로 구간 명시.
- 클래스 `@DisplayName` 은 비즈니스 도메인 용어로 간결하게 작성. `*Test`, `*규칙 테스트`, `*서비스` 같은 개발자 용어 접미사 금지.
- 메서드 이름은 "조건일 때 결과" 패턴 또는 한국어 자연 문장. 한국어 사용 시 `@DisplayName` 어노테이션 활용.
- 예외 발생 케이스는 "예외가 발생한다" 로 통일 (기술 명칭 미포함).

## 리팩터링 = 작동 보존 증거

리팩터링 후에는 변경 전과 동일한 작동을 유지함을 증거로 보여야 한다.

- 기존 테스트 전체 통과가 1차 증거.
- 기존 테스트가 없는 영역을 리팩터링한다면, 변경 전에 작동 보존 테스트를 먼저 추가해서 변경 전 작동을 캡처한다 (별도 `test:` 커밋으로 분리해서 리팩터링 커밋보다 앞에 둔다).
- 통합 테스트에서는 API 호출 결과(status, body, 헤더)가 변경 전후 동일한지 비교한다.
- 도메인 정책 테스트에서는 입력 -> 출력 매핑이 변경 전후 동일한지 비교한다.

위 증거 없이 "테스트 통과" 만으로 리팩터링을 끝내지 않는다. 통과한 테스트가 실제 작동을 충분히 캡처하는지 한 번 더 확인한다.

## 테스트 회피 금지

다음 패턴은 발견 즉시 되돌린다.
- `@Disabled`, `@Ignore` 부착 (이유 명시 + 사용자 승인 없으면 금지).
- assertion 제거 또는 약화 (`assertEquals` -> `assertNotNull` 같은 다운그레이드).
- try/catch 로 실패를 삼키는 패턴.

테스트가 실패한다면 원인을 먼저 본다. 회피는 답이 아니다.

## 실행 명령

```
./gradlew test          # 전체 테스트
./gradlew check         # 테스트 + 빌드 검증
./gradlew build         # 전체 빌드 (테스트 포함)
```

외부 API 호출 테스트는 `@Tag("external-api")` 로 격리하고, CI 에서 제외할지는 사용자와 합의 후 결정한다.
