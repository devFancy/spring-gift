# spring-gift

카카오 선물하기 도메인의 백엔드 서버를 리팩터링하는 미션. 기존의 평면 패키지(Controller가 데이터 접근까지 직접 호출하는 구조)에서 도메인별 책임이 분리된 구조로 정리한다.

기능 목록 단위로 커밋을 분리한다. AngularJS Git Commit Message Conventions 와 같은 형식으로 `<type>(<scope>): <한국어 제목>` 을 사용한다.

- [x] 작업 환경 가이드 - 코드 작업 가드레일과 작업 흐름 룰을 저장소에 함께 보관
- [x] 전역 응답/에러 처리 - 모든 API 응답을 같은 모양으로 감싸고, 예외도 같은 흐름으로 처리
- [x] 통합 테스트 베이스 - 테스트 실행 전 자동 초기화되는 진입점 신설
- [x] 상품 카탈로그 - 상품 등록/조회/수정/삭제 흐름을 도메인 단위로 분리, ControllerTest와 ServiceTest 함께 작성
- [x] 회원 가입과 로그인 - 회원 등록과 인증 토큰 발급 흐름을 응용 서비스로 정리, ControllerTest와 ServiceTest 함께 작성
- [x] 선물 위시리스트 - 위시리스트 담기/삭제 흐름과 소유자 검증 정책 정리, ControllerTest와 ServiceTest 함께 작성
- [x] API 버저닝과 문서 스니펫 - URL에 v1 버전 명시, 통합 테스트 실행 시 API 문서 스니펫 자동 생성
- [x] 빌드 설정 정리 - Java 전용 프로젝트와 어긋난 빌드 설정 제거
- [x] 카테고리 - 같은 패턴 적용, ControllerTest 로 외부 계약 검증
- [x] 상품 옵션 - 같은 패턴 적용, ControllerTest와 ServiceTest 함께 작성
- [x] 주문 - 같은 패턴 적용, 카카오 메시지 클라이언트 분리, ControllerTest와 ServiceTest 함께 작성
- [x] 카카오 로그인과 인증 - OAuth 클라이언트, 토큰 발급/검증, ArgumentResolver 분리, ControllerTest와 ServiceTest 함께 작성
- [x] 도메인 객체와 JPA 엔티티 분리 - 도메인 계층을 JPA 의존 없이 순수 Java 클래스로 구성, 값 객체(VO) 도입으로 도메인 규칙 캡슐화
- [x] 비밀번호 암호화 - 로그인 시 평문 비교에서 SHA-256 해시 비교로 전환
- [x] 주문 시각 생성 외부 주입 - LocalDateTime.now() 하드코딩 제거, ClockHolder 인터페이스로 교체해 테스트 제어 가능
- [x] 카카오 메시지 전송 실패 로깅 - 예외를 완전히 무시하던 코드에 warn 레벨 로그 추가
- [x] 상품명 카카오 정책 맥락 분리 - boolean 파라미터 제거, 일반 API와 운영자 화면의 흐름을 명시적 메서드로 분리
- [x] 도메인 모델링 문서화 - 용어 사전과 도메인별 속성/행위/정책을 `docs/gift-domain-modeling.md` 에 정리

## 구현 전략

### 패키지를 도메인 흐름 단위로 분리

기존엔 `gift/product/`, `gift/member/` 안에 Controller, Repository, Entity, Validator 가 평면적으로 섞여 있었다. 본 리팩터링에서 같은 도메인 안의 역할을 다음 6개 영역으로 분리한다.

- `api` 사용자 요청을 받고 응답을 돌려보내는 진입점.
- `application` 비즈니스 흐름을 조립하고 트랜잭션 경계를 잡는 응용 서비스.
- `domain` 도메인 규칙과 정책이 모이는 자리(예: 상품명에 "카카오" 사용 정책, 회원 이메일 중복 정책).
- `infrastructure` 외부 시스템과 연결(카카오 OAuth, 카카오 메시지, 토큰 발급/검증).
- `storage` 데이터베이스 접근(JPA Entity, Repository).
- `support` 전 영역이 공유하는 응답 형식과 에러 타입.

### 비즈니스 용어를 코드와 커밋 메시지에 그대로 사용

도메인 흐름을 정리할 때 가장 먼저 잡은 것은 용어 사전이다. Controller, Repository, Service 같은 기술 용어보다 상품 카탈로그, 위시리스트 담기, 카카오 로그인 같은 도메인 용어를 코드 안과 커밋 메시지 제목에 우선 노출한다. 
PM 이나 신입 동료가 커밋 로그만 봐도 어떤 사용자 흐름이 정리되었는지 알 수 있도록 한다.

### 리팩터링 한 조각씩 단계적으로 진행

도메인 하나를 정리할 때 다음 순서를 따른다.

1. 변경 전 작동을 캡처하는 통합 테스트를 먼저 추가한다 (`test:` 커밋).
2. 도메인을 6개 영역으로 분리하고 응답 형식을 일관화한다 (`refactor:` 커밋).
3. 변경 후 전체 테스트가 그대로 통과하는지로 작동 보존을 증명한다.

한 커밋에는 한 가지 의도만 담는다. 리팩터링과 테스트 추가가 한 커밋에 섞이지 않게 분리한다.

### 도메인 객체와 JPA 엔티티를 분리해 가독성을 높인다

코드를 오래 유지보수하려면 비즈니스 규칙이 어디 있는지 한눈에 보여야 한다. 기존엔 JPA `@Entity` 클래스가 영속성 매핑과 도메인 행위를 동시에 담고 있어서 둘을 분리해 읽기 어려웠다.

본 리팩터링에서 도메인 객체(`domain/`)와 JPA 엔티티(`storage/*Entity`)를 완전히 나눴다.

- `domain/{domain}/` 비즈니스 행위와 불변식만 담는 순수 Java 클래스. JPA 어노테이션 없음.
- `domain/{domain}/vo/` 값 객체. 생성자에서 형식/범위 검증을 수행해 잘못된 값이 도메인 안으로 들어오지 못하게 막는다(예: `ProductName` 은 15자 초과와 허용되지 않는 특수문자를 생성자에서 차단한다).
- `storage/{domain}/*Entity` JPA `@Entity`. 도메인 객체로 변환하는 `toDomain()` 과 `from()` 메서드를 보유한다.

이 구조에서 비즈니스 규칙을 읽으려면 `domain/` 만 보면 된다. 어떻게 저장되는지는 `storage/` 에서 독립적으로 파악할 수 있다.

### 통합 테스트와 문서를 함께 다룬다

핵심 사용자 시나리오는 통합 테스트로 검증한다(`@SpringBootTest` + 테스트 전 DB 초기화). 같은 테스트가 실행될 때 API 문서 스니펫이 자동 생성된다(REST Docs). 통합 테스트의 클래스 이름은 `{Domain}ControllerTest`, `@DisplayName` 은 도메인 비즈니스 어휘로 작성한다.

### 과제의 기능 요구사항 매핑

본 과제가 요구하는 리팩터링 항목과 본 작업의 적용을 한 줄로 매핑한다.

| 기능 요구사항 | 본 작업에서의 적용 |
| --- | --- |
| 코드 스타일 정리 | 코딩 컨벤션을 `.claude/rules/coding-convention.md` 룰로 박아 모든 변경에 자동 적용 (들여쓰기 깊이 2, 메서드 15줄, 도메인 어휘 우선 등) |
| 불필요한 코드 제거 | 가치 낮은 테스트 정리, 사적 javadoc 메타 제거, `@Autowired` 같은 redundant 어노테이션 생략 |
| 서비스 계층 추출 | 7개 도메인 모두 `application/*/Service` 신설. Controller 는 인증/응답 변환만 담당하도록 얇게 정리 |
| 트랜잭션 경계 명시 | Service 클래스 상단 `@Transactional(readOnly = true)` 기본, CUD 메서드에만 `@Transactional` 명시 |
| 누락된 작동 구현 | 비밀번호 평문 저장을 SHA-256 암호화로 전환. 카카오 메시지 전송 실패를 로그 없이 무시하던 코드에 warn 로그 추가 |
| 도메인 책임 회수 | 도메인 객체와 JPA 엔티티 분리. 값 객체(VO) 도입으로 형식 검증과 도메인 규칙을 도메인 계층 안에 캡슐화. 주문 시각 생성을 `ClockHolder` 인터페이스로 추상화해 테스트 가능하게 전환 |

## AI 도구 활용 기록

본 프로젝트는 Claude Code 와 함께 진행했다. 
"코드를 대신 짜 주는" 자유 방임이 아니라 AI 가 일할 작업 환경 자체를 먼저 설계해서 그 안에서 실행하는 방식을 택했다. 
통제 범위는 세 층(`CLAUDE.md` 프로젝트 컨텍스트, `.claude/rules/` 매번 자동 적용 가드레일, `.claude/skills/refactor-step/` 호출 시점 워크플로우) 으로 분리하고, 
모든 작업은 계획 제안 -> 사용자 승인 -> 실행 의 plan-first 흐름과 종료 직전 7개 자가 점검을 자동 수행하도록 박아 두었다.

### 작업 흐름 합의

매 작업의 시작 단계는 다음 3단계로 분리했다.

1. 계획 제안: 변경 파일 목록, 각 파일 책임, 순서, 검증 방식을 먼저 한 화면 분량으로 제시받는다. 코드는 건드리지 않는다.
2. 사용자 승인: 계획을 검토하고 명시적으로 OK 하면 다음 단계로 넘어간다.
3. 실행: 승인된 계획대로만 적용한다. 계획에서 벗어난 변경이 필요해지면 즉시 멈추고 다시 합의한다.

이 흐름은 `.claude/rules/plan-execute-discipline.md` 룰로 박아 두어 매 작업마다 자동으로 적용된다.

### 가드레일을 저장소에 함께 보관

작업 환경 자체를 git 에 박아 두면 다음에 같은 작업을 다시 할 때 같은 품질이 보장된다. 본 프로젝트는 다음을 저장소에 함께 보관한다.

- `CLAUDE.md` 프로젝트 수준 컨텍스트(패키지 구조, 커밋 규약, 카카오 로그인 가정 등).
- `.claude/rules/` 매번 자동 적용되는 가드레일 8개(커밋 규율, 코딩 컨벤션, 리팩터링 원칙, 테스트 원칙, 표기 규약, 세션 관리, 자가 점검, 계획-실행 분리).
- `.claude/skills/refactor-step/` 리팩터링 한 조각을 단계적으로 진행하는 워크플로우 스킬.

### 반복 사용한 패턴

- 모호한 명령은 코드를 건드리기 전에 5개 이내 질문으로 좁힌다(범위/우선순위/검증 기준/자율 영역).
- 새 룰이나 스킬은 같은 보강을 두 번 이상 떠올렸을 때만 추가한다. 한 번만으로는 만들지 않는다.
- 매 작업 종료 직전 7개 자가 점검을 자동 수행한다(산출물 목록, 단일 책임, 표기, 룰/스킬 역할 분리, 패키지 위치, 커밋 규율, 회피 패턴 부재).
- 작동 보존 테스트는 응답 본문의 세부 모양보다 상태 변화(데이터베이스, 상태 코드)를 중심으로 검증한다. 응답 형식이 변해도 비즈니스 흐름의 보존을 증명할 수 있도록 한다.

### 실제 사용한 프롬프트 예시

명령은 짧고 단일 목적으로 좁혀 호출한다. 의도를 한 줄에 박아 두면 AI 가 어떤 모드(범위 좁히기 / 단일 목적 분리 / 컨벤션 근거 확인)로 답해야 하는지 분명해진다.

- `/refactor-step 주문 흐름을 6계층으로 정리하고 카카오 메시지 클라이언트를 infrastructure/oauth 로 이동` - 변경 한 조각의 범위 좁히기. `/refactor-step` 스킬이 단일 목적 확인 -> 범위 좁히기 -> 적용 -> 검증 -> 커밋 승인 5단계를 자동 진행.
- "주문 영역에 작동 보존 테스트 먼저 추가하고, 6계층 정리는 별도 커밋으로 분리해" - 단일 목적 분리. 리팩터링과 테스트 추가가 한 커밋에 섞이지 않도록 작동 보존 테스트(test:) -> 구조 정리(refactor:) -> 추가 통합 테스트(test:) 3개 커밋으로 분할 적용.
- "OrderDto 가 wrapper + 중첩 record 구조인데 이게 적합한가" - 컨벤션 근거 확인. 다른 도메인(상품, 옵션, 위시리스트 등) 이 모두 같은 패턴을 쓰는 이유, record 자체의 이점과 wrapper 의 응집 효과를 분리해서 검토 후 일관성 유지로 결정.

### 학습한 점

- 작업 가드레일 자체를 저장소에 박아 두면 다음 작업이 같은 품질로 다시 진행된다. 사람이 매번 똑같은 톤으로 검수하지 않아도 된다.
- 단일 목적 커밋은 리뷰어를 위한 장치이기도 하지만 작성자 본인이 작업 범위를 좁히는 도구로 더 강하다. "지금 이 커밋에 들어가도 되는 변경인가" 를 매 변경마다 묻게 된다.
- AI 가 제시한 사실(예: "이 어노테이션은 생략 가능") 은 별도 출처 확인 후 채택한다. 검증 없이 받아들이면 코드에 그럴듯한 거짓이 박힌다. 출처는 코드 옆이 아니라 별도 research 문서로 분리해 라우팅한다.

### 구체적 상호작용 사례

- 카테고리 영역의 `ServiceTest` 가치 평가. ControllerTest 가 이미 외부 계약과 상태 변화를 모두 검증하는데 ServiceTest 가 같은 시나리오를 다시 한 번 검증하고 있었다. 다른 도메인(상품 옵션, 주문, 위시리스트)의 ServiceTest 가 도메인 정책 분기와 idempotent 보장 같은 ControllerTest 가 닿지 않는 시나리오를 담는다는 점과 대비해, 카테고리는 단순 CRUD 라 ServiceTest 자체가 가치 없다고 판단했다. 통째 삭제 결정 후 다른 도메인과 일관성 재점검까지 한 번의 상호작용으로 마무리.
- `@ModelAttribute` 의 명시 여부 결정. 외부 reference 프로젝트가 어노테이션을 생략한다는 관찰에서 출발해, Spring MVC 의 매개변수 해석 규칙과 record canonical constructor binding 동작을 사실 기반으로 확인했다. 결정 근거는 `docs/private/research/` 의 별도 문서로 분리하고, 코드 옆에는 한 줄 주석만 남겼다. 추가로 통합 테스트 두 개로 작동 보장을 증거화.

### 의사 결정의 책임

AI 가 작성한 코드는 초안이며, 설계와 검증의 책임은 본인에게 있다. 중간 결과물의 의도하지 않은 변경은 즉시 제거하고, 커밋 직전 git diff 를 사람이 직접 한 번 더 확인한다. AI 가 자율로 결정하는 영역과 사용자 합의가 필요한 영역을 매번 분리한다.

## 카카오 로그인 사용 시 설정 (선택)

카카오 API 애플리케이션 등록은 본인이 직접 처리한다. 등록 후 `application.properties` 의 다음 값을 채운다.

- `kakao.login.client-id`
- `kakao.login.client-secret`
- `kakao.login.redirect-uri` (예: `http://localhost:8080/api/auth/kakao/callback`)

운영 환경에서는 환경 변수로 주입한다. 어드민 키, 액세스 토큰, 클라이언트 시크릿은 저장소나 클라이언트 코드에 절대 포함하지 않는다.
